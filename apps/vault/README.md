# @bc/vault

The Concepts Vault server: a Cloudflare Worker that serves the Vault API (`/api/v1`) over D1 (records) and R2 (files), behind Cloudflare Access. This package is wiring only. The business logic is in `packages/core`, the records and routes in `packages/contract`.

## Parts

| File | What |
|---|---|
| `src/index.ts` | Worker entry. Adds security headers. Exports the `VaultPublic` entrypoint |
| `src/app.ts` | Builds the app from D1, R2 and the sign-in setting |
| `src/d1-store.ts`, `src/sql.ts` | The Store over D1 (one `records` table, record as JSON) |
| `src/auth.ts` | Checks the Cloudflare Access token; one allowed email; fails closed |
| `src/r2-files.ts` | File bytes in R2 |
| `src/entrypoint.ts` | The only door the Hub has: six methods, via a service binding |
| `src/testing-sqlite.ts` | Runs the same SQL on `node:sqlite` for tests (not in the Worker bundle) |
| `migrations/` | Database schema, applied with `wrangler d1 migrations apply` |
| `seed/` | `base.sql` for a new deployment; `dev.sql` fictional data for local use (generated by `npm run seed:sql`) |
| `wrangler.jsonc` | Bindings and settings. Placeholders to fill in: see `docs/DEPLOY.md` |

## Commands

```
npm test              # store conformance, sign-in and boundary tests, and the whole story on SQLite
npm run typecheck
npm run build:check   # bundle the Worker exactly as a deploy would (no upload)
npm run seed:sql
npm run dev           # wrangler dev --local
```

## Rules

1. No business logic here. If a route behaves wrongly, fix `packages/core` so the mock and this server stay identical.
2. Every change to the schema is a new numbered file in `migrations/`; never edit one that has been applied.
3. The Hub gets no database or R2 binding. It reaches the Vault only through `VaultPublic`.
4. Secrets never go in `wrangler.jsonc` or the repo. (There are none yet: the Access values are not secret.)
